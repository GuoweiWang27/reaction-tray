## 1. 本版结论

V1.1 保留 V1.0 的核心玩法和 React + TypeScript + Vite 技术路线，但不把概念关卡表当成可执行关卡。开发分成两个门：

1. 先完成第 1～3 关垂直切片，验证取牌、遮挡、7 格槽、比例反应、动画效果、目标、失败和原子撤回；
2. 垂直切片通过自动化验证、化学审核和 5～8 人观察测试后，才开始第 4～20 关内容生产。

首阶段不实现安全重排、完整图鉴、章节地图、背景音乐、统计后端、登录或 AI。

## 2. 权威边界

- `src/content/species.ts`：物质机器数据真源；展示公式不得承担守恒计算。
- `src/content/reactions.ts`：17 条核心反应真源；关卡和图鉴只引用反应 ID。
- `src/content/levels/`：可执行关卡真源；每关必须包含固定牌局、遮挡图和标准解。
- `src/game/engine/`：唯一游戏状态转移实现；UI 和求解器不得复制规则。
- `scripts/validate-content.ts`：内容发布门；化学审核仍是独立人工门。

## 3. 一次玩家操作的确定顺序

外部命令只有取牌、选择条件、撤回、提示、重开。一次取牌或条件选择及其全部自动反应构成一个事务：

1. 校验命令是否合法；
2. 保存命令前领域状态快照；
3. 应用取牌或条件；
4. 按关卡内优先级寻找唯一可触发反应；
5. 先移除反应物，再写入产物记录和指定中间体；
6. 消耗本次反应使用的一次性条件，保留持续催化条件；
7. 重复第 4～6 步直到没有可触发反应；
8. 更新目标并优先判断胜利；
9. 未胜利时判断槽状态；
10. 把领域效果交给 UI 播放；动画完成不改变化学结果。

槽状态只有三种：

- 槽未满：继续取牌；
- 槽已满，但激活本关可用条件即可触发反应：进入 `awaiting-condition`，禁止继续取牌但允许选择该条件；
- 槽已满且不存在可触发反应或可使反应触发的条件：失败。

棋盘无可选牌且目标未完成时失败。`完整扫描后无反应` 不能单独作为失败条件。

## 4. 反应选择与条件生命周期

- 只解析当前关卡 `allowedReactions`。
- 游戏优先级属于关卡，不属于全局反应定义。
- 同一状态出现两条同优先级可触发反应时，内容校验失败；运行时不得猜测。
- `ignite`、`heat`、`light` 为一次性条件：参与一次反应后清除。
- `mno2` 为持续催化条件：激活后保留到关卡结束或撤回到激活前。
- 一次只允许一个能量条件激活；持续催化条件可以和一个能量条件并存。
- `RESOLVE_REACTION` 是引擎内部过程，不是 UI 可伪造的玩家命令。

## 5. 撤回契约

- 撤回恢复最近一次玩家命令之前的完整领域状态。
- 一次取牌引起的全部自动/连锁反应只占一个撤回历史帧。
- 撤回恢复棋盘、槽、条件、产物、目标进度、反应次数、步数和状态。
- 动画队列不进入领域状态；撤回时 UI 取消未完成动画并渲染恢复后的状态。
- 垂直切片每关提供 1 次撤回；求解器证明可解时不使用道具。

## 6. 化学表达修订

- 第 1～3 关明确使用水溶液中的净离子式；卡牌可访问名称必须包含“水溶液中的……离子”。
- 后续使用分子式表达同一本质反应时，必须通过反应闪卡说明旁观离子和两种表达之间的关系。
- 删除 V1.0 第 7 关“混入 CaCO3 但禁止其与 HCl 反应”的设计。后续二选一：开放两条真实反应，或更换在声明条件下不反应的干扰物。
- H2/O2 点燃、Mg 燃烧、AgCl 光解产生 Cl2、CO 炼铁和可溶性钡盐关卡必须有安全文案审核；游戏不得给出可执行实验步骤。
- 结构化元素组成和电荷用于自动守恒检查；人工审核负责物态、条件、教育阶段适切性和简化边界。

## 7. 垂直切片关卡契约

精确卡牌、坐标、遮挡关系和标准解由 `src/content/levels/vertical-slice.ts` 承载。本阶段冻结：

| 关卡 | 目标 | 槽容量 | 关键机制 | 标准解要求 |
|---|---|---:|---|---|
| 1 第一滴水 | 3 H2O | 8 | 强引导、1:1、两层遮挡 | 不使用道具，所有目标牌均被取出 |
| 2 银色迷雾 | 3 AgCl | 7 | 沉淀、无反应干扰牌 | 不触碰 H+ 干扰牌即可完成 |
| 3 蓝色沉淀 | 2 Cu(OH)2 | 7 | 1:2、标准槽、撤回与失败 | 至少一条安全路线和一个可恢复错误 |

生产目标关卡允许留下未取的干扰牌；只有“清空目标卡”关卡才要求每张牌都有消除路径。因此 V1.0 的“所有干扰牌必须安排合法消除路径”不再作为全局约束。

## 8. 求解器契约

- 求解器调用生产引擎的纯状态转移函数，不维护第二套规则。
- 搜索状态包含剩余 tile ID、槽内 tile/species、条件状态、目标进度、顺序目标索引和游戏状态。
- 哈希排除动画、用时、音效和 UI 状态；无道具可解证明也排除道具次数。
- 标准提示不能只保存初始路线索引；玩家偏离路线后必须从当前状态重新搜索。
- 安全重排首阶段为 0 次。未来恢复时，必须对“当前剩余牌状态 + 候选重排”重新求解，不能只证明初始牌局可解。
- CI 中每关设置节点数和耗时上限，并输出最短取牌数、搜索节点、分支数和安全首步集合。

## 9. 数据与评分修订

- `SpeciesDefinition` 保存机器公式、展示公式、元素组成、电荷和默认显示物态。
- 物态最终以 `ReactionTerm.phase` 为准。
- `ConditionDefinition` 保存类别和生命周期。
- `LevelDefinition.allowedReactions` 保存关卡内优先级。
- `sequence` 目标必须保存有序步骤数组，不再使用单一 `targetId + count`。
- 三星规则显式包含 `maxTools: 0` 和最大步数；不再依赖无法表达的“或连锁目标”。
- 化学审核元数据包含状态、审核人、日期、版本；未审核内容可以开发，但不能进入发布包。

## 10. UI、无障碍和测试边界

- 设计基准为 390 x 844，同时验证 360 px 宽度。
- 化学式、名称、物态和图形标识共同识别物质；颜色不是唯一信息。
- 所有可点击卡和按钮支持键盘焦点与可访问名称。
- 反应完成、目标更新、槽警告和失败原因使用可访问状态消息播报。
- 减少动态效果模式取消飞行、闪光和抖动，用短淡入淡出替代。
- Playwright 设备模拟用于回归；发布前仍需至少一次真实 iOS Safari 和 Android Chrome 手工检查。

## 11. 验证门

垂直切片必须同时满足：

- 类型检查、lint、Vitest、生产构建通过；
- 17 条反应元素守恒，适用表达中的电荷守恒；
- 第 1～3 关内容引用、遮挡图和标准解校验通过；
- 第 3 关正确覆盖正常反应、错误取牌、槽满失败和原子撤回；
- Chromium 与 WebKit 的 390 px 完整流程通过；
- 360 px 无关键溢出、遮挡或不可点击目标；
- 化学审核人对前三关签字；
- 5～8 名目标用户中多数能解释第 3 关为何需要 1 个 Cu2+ 和 2 个 OH-。

未满足门槛时，优先修正规则、提示或牌局，不开始第 4～20 关批量制作。

## 12. 修订后的时间盒

1. 准备期（1～2 天）：仓库、规则、类型、17 条反应结构化数据、前三关精确牌局；
2. 垂直切片（5～7 个开发日）：引擎、求解器、1～3 关 UI、撤回和自动化测试；
3. 门槛测试（2～3 天）：化学审核、5～8 人观察测试、修复；
4. 内容扩展（约 2 周）：按已验证模板制作 4～20 关；
5. 发布验证（至少 1 周）：完整 QA、15～30 人测试和修复。

四周可作为“20 关可玩构建”的挑战目标，不把完整用户研究结论和正式发布同时塞入该承诺。
